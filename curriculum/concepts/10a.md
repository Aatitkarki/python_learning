## Before the exercises: Failures, logs, and recovery

### Concepts in plain language

Reliability means the service handles expected work and failures predictably. Liveness asks whether a process is alive; readiness asks whether it can serve useful requests, including needed dependencies. A live process with an unavailable database may be unready.

Logs record events, metrics aggregate quantities, and traces connect steps in a request. A request ID joins observations without copying sensitive inputs. Measure latency and error rate alongside success counts.

A fault-injection test deliberately makes a dependency fail, then checks response, timing, disclosure, and recovery. A mock is useful for a reproducible unit test; a real stopped service provides different integration evidence.

### Worked example: follow the values

Make the database repository raise an operational error containing a private internal string. The client should get a generic 503 without that string. Restore the repository, repeat an authenticated read, and check the expected data. A successful health endpoint alone does not establish recovery of data access.

### Common mistakes to check

Never log credentials or raw private documents to make debugging easier. Record explicit recovery evidence, not only the injected failure.
